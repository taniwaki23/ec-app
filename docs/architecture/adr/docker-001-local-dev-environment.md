# ADR docker-001: ローカル開発環境の構成

- 日付: 2026-09-27
- ステータス: 採用

## 背景

ec-app(FastAPI + PostgreSQL)をローカルで開発する環境を決める。
実装は AI(Claude Code)に書かせ、人間が動かして検証する往復を何度も繰り返す開発スタイルである。
同じPC上では、SQL練習用の PostgreSQL コンテナ `pg16` が 5432 番ポートで常駐している。

## 決定

### 1. docker compose でアプリと DB をセットで起動する

- 理由: 1コマンド(`docker compose up`)で起動でき、構成が `compose.yaml` に残るため、誰がやっても同じ環境を再現できる。
- 捨てた案:
  - PostgreSQL を Windows に直接インストールする — 環境が人によって変わり、再現できない。
  - `docker run` で1つずつ起動する — 手順が増え、構成が記録に残らない。
- 代償: Docker / compose の知識が必要。Docker Desktop のメモリ消費が増える。

### 2. ec-app の DB は 5433 番で公開する

- 理由: 学習中のため、Windows 上のツールからも DB を直接操作したい。5432 番は `pg16` が使用中で、重なると後から起動した側が起動できない。
- 捨てた案:
  - ポートを公開しない — 最も安全だが、Windows 上のツールから接続できない(`docker compose exec` での psql は可能)。
  - 5432 番で公開し、使うときに `pg16` を止める — 切り替えの手間があり、止め忘れるとエラーになる。
- 代償: 接続時に 5433 を意識する必要があり、既定値(5432)との食い違いで設定ミスが起きやすい。
- 見直す条件: 本番相当の構成では DB のポートは公開しない。

### 3. ホットリロードを使う

- 理由: 保存のたびにイメージを build し直すと毎回時間がかかる。AIに書かせて動かして確かめる往復が多いため、保存したら自動で反映される環境で検証を速く回したい。
- 捨てた案: 変更のたびに build して再起動する — 1回あたり数十秒〜数分かかり、検証の回数が減る。
- 代償: Windows のフォルダをコンテナから読む構成では、変更が反映されないことがある。開発(コードを外からマウント)と本番(コードをイメージに含める)で動かし方が違うため、ときどき本番と同じ方法でも確認する必要がある。

### 4. 作業フォルダは Windows 側(`C:\Users\<ユーザー>\projects\ec-app`)に置く

- 理由: まだアプリのコードがなく、ホットリロードの問題は起きていない。慣れた Windows の操作で進められ、WSL の準備(Ubuntu の導入)に時間を使わずに済む。
- 捨てた案: WSL(Linux)側に置く — ファイルの読み書きが速く、ホットリロードも確実に効き、本番に近い。ただし Ubuntu の導入と Linux 操作への慣れが必要。
- 代償: ホットリロードが遅い、または効かない可能性がある(決定3の代償と同じ原因)。
- 見直す条件: アプリを動かし始めて、変更が反映されない問題が出たら WSL 側に移す(まずはポーリング方式の監視を試す)。
