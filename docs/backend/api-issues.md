# API の論点メモ(2026-10-07)

入力: `docs/frontend/screens.md`(バックエンドへの要求)、`difficulties.md`、`architecture/nfr.md`、`db/normalization.md`

1. 注文一覧のページング・絞り込み・並べ替えをどうするか(根拠: screens.md)
2. 注文の状態変更で、同時更新(楽観ロックと 409)をどうするか(根拠: screens.md)
3. 注文確定の冪等性(同じ依頼が2回届いたとき)をどうするか(根拠: screens.md)
4. 利用者の種類(顧客・管理者・店舗スタッフ・倉庫担当)ごとに API のパスをどう区切るか(例: `/me/orders` と `/admin/orders`)
5. 認証(呼んでいるのが誰かをどう確かめるか。ログインとトークン)をどうするか
6. 認可(その人にその操作・そのデータが許されているか)をどうするか。ロールの確認(顧客が /admin を呼べない)と所有者の確認(他人の注文を取れない)をどの層で行うか
7. エラー形式をどう統一するか(どの失敗にどのステータスコードを返すか、本文の項目、500 で内部情報を出さないこと)
8. 在庫が1個のときに同時に注文が来ても売りすぎないよう、在庫を減らす処理の同時実行(競合状態)をどう防ぐか
9. 注文後に価格が変わっても注文時の金額を返せるよう、購入時の単価をどこに固定するか(注文明細にコピー)。注文確定の価格はクライアントから受け取らず、サーバーで決めるか
10. 性能の目標(応答時間・1回に返す件数の上限・データ量の想定)が nfr.md にないので、どう決めるか
