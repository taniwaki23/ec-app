# 正規化演習の記録

題材: 1枚の「注文伝票」表(注文番号・注文日・顧客名・顧客住所・商品名1〜n・単価1〜n・数量1〜n)を正規化する。

## 第1正規形(2026-09-28)

- 問題: 「商品名1、商品名2…」の繰り返しの列。入れられる商品数に上限ができる、空欄だらけになる、「ペンが何個売れたか」を数えるのに全列を調べる必要がある。
- 対応: 繰り返しを行にする。**注文明細**(注文番号 + 商品で1行、数量を持つ)を作る。注文と商品は多対多で、注文明細が中間テーブル(dvdrental の film_actor と同じ形)。

## 第2正規形(2026-09-28)

- 問題: 注文明細の主キーは「注文番号 + 商品」だが、単価は商品だけで決まる(部分関数従属)。値上げのたびに全明細を直す必要がある(更新時異常)。
- 対応: **商品**(商品、単価)を分ける。
- 実務の判断: 値上げで過去の注文の金額が変わってはいけないので、注文明細に **購入時単価** を持たせる。「今の値段」と「買った時の値段」は別の事実。

## 第3正規形(2026-09-29)

- 問題: 注文の表で、住所は注文番号ではなく顧客名で決まる(推移的関数従属: 注文番号 → 顧客名 → 顧客住所)。
- 対応: **顧客**(顧客ID、名前、住所)を分け、注文には外部キーの顧客IDだけを残す。
- 判断: 主キーは名前ではなく **顧客ID**(同姓同名の区別、名前の変更に対応するため)。自分で気づいた判断。商品にも同じ理由で商品IDを付ける。
- 実務の判断: 配送先住所は、引っ越しても過去の注文の配送先が変わらないよう、注文にコピーして持つ(時点の固定)。

## 完成形

- 顧客(**顧客ID**, 名前, 住所)
- 注文(**注文番号**, 注文日, 顧客ID → 顧客, 配送先住所)
- 注文明細(**注文番号 → 注文, 商品ID → 商品**, 数量, 購入時単価)
- 商品(**商品ID**, 商品名, 単価)

## 正規化しないと起きる3つの異常

| 異常 | 何が起きるか | 例 |
|---|---|---|
| 更新時異常 | 同じ情報を何か所も直す必要があり、直し漏れると矛盾する | 田中さんが引っ越すと、全部の注文の行を直す |
| 挿入時異常 | ある情報がないと、別の情報を登録できない | 注文がないと、新しい顧客・まだ売れていない商品を登録できない |
| 削除時異常 | ある情報を消すと、別の情報まで消える | 鈴木さんの唯一の注文を消すと、顧客情報も消える |

## 面接での一言

「データの重複をなくして、更新・挿入・削除のときの矛盾を防ぐための設計です。ただ、注文時の単価や配送先のように時点を固定したい値は、あえて注文側に持たせます。」
