# 複雑な機能の「難しさリスト」

設計の出発点。各項目は後で ADR・実装仕様・レビュー観点・テストに展開する。

## 機能A: 管理画面の注文一覧(2026-09-29)

想定: スタッフ2〜3人(店長・アルバイト)。注文は年約18,000件。
代表操作: 「3日以上前の未出荷の注文」を絞り込み、10件を選んで「まとめて出荷準備」にする。

| # | 難しさ | 起きること | 対策の方向(判断は ADR で) |
|---|---|---|---|
| 1 | まとめて操作の **部分失敗** | 選んだ10件に、他のスタッフが処理済みの注文が混ざる | 全部取り消すか、成功分だけ反映して失敗分を知らせるか |
| 2 | **ページをまたいだ選択** | ページ移動で選択が消える。何を選んだか見えない。「すべて選択」の範囲が曖昧 | 選択状態の置き場所、「〇件選択中」の常時表示、「このページ / 条件に合う全件」の区別 |
| 3 | **絞り込み条件の保持** | 再読み込み・URL共有・「戻る」で条件が消える | 条件は **URL のクエリを唯一の置き場所** にする。値の検証、条件変更時は page=1、履歴の残し方 |
| 4 | **競合状態** | 条件を素早く切り替えると古い返事が後から届き、条件と一覧が食い違う(エラーは出ない) | 古い問い合わせの取り消し / 古い返事を捨てる / データ取得ライブラリで条件ごとに管理 |
| 5 | **タイムアウト時の結果不明** | 処理が終わったか分からない。やり直すと二重実行の危険 | 「失敗」と「結果不明」を区別して表示、やり直す前に最新状態を読み直す、BE で冪等性 |
| 6 | **権限による出し分け** | アルバイトにキャンセルさせない | 画面の出し分け(非表示か、押せない状態+理由表示か)+ **サーバーでも必ず確認(403)** |
| 7 | **古いデータ** | 開いたままの画面で、他人の更新が反映されていない | タブに戻ったら再取得 + 保存時は楽観的ロック。リアルタイムは費用に見合うか判断 |
| 8 | **0件・エラー・読み込み中の区別** | エラーなのに「0件」と表示すると「注文がない」と誤解される | 3状態を区別、絞り込み条件の表示、「条件をクリア」 |

(ページング → サーバー側、同時更新 → 楽観的ロックは screens.md で判断済み)

## 繰り返し出てきた原則

- **フロントの対策は使いやすさのため、サーバーの確認は安全のため。** フロントだけの対策(プルダウン、ボタン無効化、ボタン非表示)では守れない。
- **静かに間違う不具合(エラーが出ない食い違い)が一番危ない。** 競合状態、エラーを0件と表示、など。
