# 画面一覧と非機能要件(v0.1)

- 作成日: 2026-09-29
- 利用者: 顧客 / 店舗スタッフ(管理者)

## 範囲の判断

- **発注(仕入れ先への注文)は含めない。** 今回の目的は、注文から出荷までの中心の流れと、2つの複雑な機能(管理の注文一覧 / カート〜注文確定)を作りきること。発注は仕入れ先の管理・発注書・入荷登録などが必要で工数が大きいため、フェーズ2で扱う。
- 受注の処理(状態の変更、出荷準備)は、独立した画面にせず、注文一覧と注文詳細の中で行う。
- 退会は独立した画面にせず、会員情報の編集画面の中に置く(誤操作を防ぐ確認の手順を挟む)。

## 顧客の画面

| 区分 | 画面 |
|---|---|
| 商品を探す | 商品一覧(検索・絞り込み)、商品詳細 |
| **注文する(複雑な機能B)** | **カート → 注文の入力(配送先・支払い)→ 注文内容の確認 → 注文完了** |
| 注文を確かめる | 注文履歴、注文詳細(状態、配送先、キャンセル) |
| 会員 | ログイン、会員登録、会員情報の編集(退会を含む) |

## 管理者の画面

| 区分 | 画面 |
|---|---|
| **受注の処理(複雑な機能A)** | **注文一覧(絞り込み・並べ替え・ページング・まとめて操作)**、注文詳細(状態の変更) |
| 商品と在庫 | 商品一覧・商品の登録/編集(価格の変更を含む)、在庫一覧(在庫の調整) |
| その他 | 管理者のログイン |

## 主な画面の非機能要件

| 画面 | データ量 | 同時に更新する人 | 失敗したときの損害 | 設計への影響 |
|---|---|---|---|---|
| **管理:注文一覧** | 1日約50件 → 年約18,000件、3年で5万件超 | あり(スタッフ2〜3人) | キャンセルされた注文を出荷してしまう | **サーバー側のページング**。初期表示は「未出荷」で絞り込む。**楽観的ロック**(保存時に他人の変更を検知して 409 で知らせる) |
| **顧客:注文の確定** | 1回の注文は数件の商品 | 同じ商品の最後の在庫を、複数の顧客が取り合う | **二重注文・二重請求・在庫の二重引当**。クレームと評判の低下 | フロントでボタンを無効化し「処理中」を表示 + **バックエンドで冪等性を保証**(フロントの対策だけでは不十分) |

## 設計判断のメモ

- **同時更新の対策に楽観的ロックを選んだ理由**: 同じ注文を同時に触るのはたまにしか起きない。悲観的ロック(編集中ロック)は、閉じ忘れでロックが残り業務が止まる損失のほうが大きい。代償として、衝突時は後から保存した人がやり直す(最新の内容を読み込み直して知らせる)。
- **ページングはサーバー側で行う**: フロントで全件を受け取ってから分ける方式では、通信とメモリの負担が変わらない。

## バックエンドへの要求(api-requirements.md に引き継ぐ)

- 注文一覧 API: サーバー側のページング、絞り込み(状態・期間)、並べ替え
- 注文の状態変更 API: 楽観的ロック(版番号などで他人の変更を検知し 409 を返す)
- 注文確定 API: 冪等性(同じ依頼が2回届いても1回として扱う)
